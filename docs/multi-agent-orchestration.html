Agent Teams

Teams of sandboxed, budget-capped, policy-scoped, audited agents that claim shared work, message peers, build on shared state, and converge — the successor to the shipped A2A orchestrator→subagent edge.

What this is, and why

The platform already runs one agent per execution (AgentRun), one durable worker per conversation (AgentSession), and a single cross-agent edge — A2A: a kind=agent tool whose invoker spawns a child run, folds its output + usage, and GC's it. That is exactly one of the five industry coordination patterns. Agent Teams generalize it to peers that coordinate.

The differentiator

Claude Code "agent teams" are single-user, single-trust, local (tmux panes, files on disk). A team here is the opposite axis: every member is an isolated, governed workload that can even span trust levels. The thing the docs call the biggest team risk — "two teammates editing the same file leads to overwrites" — we solve with branchable, 3-way-mergeable AgentFS instead of telling users to partition files by hand.

The phases — each independently shippable + governed

P0 AgentTeam CRD + governance envelope

The durable team record. Validates the team, rolls member usage up field-wise (never Usage.Add; cost never gates), and is the OwnerReference GC root for the member subtree (delete the team → its members GC). maxMembers width cap = the A2A MaxDepth analog.

agentteam.go · agentteam_controller.go · CRD + webhook

P1 Shared task list

Members claim work from a per-team NATS JetStream KV bucket. A claim is atomic (revision CAS) so no two members win the same task; a task is claimable only once its dependencies complete (fail-closed on a dangling dep).

pkg/teamtask · invoker kind=task

P2 Peer mailbox + per-member ACL

Any member messages any other by name. A per-member NATS credential lets it publish any teammate's inbox but subscribe only its own leaf — provable isolation (a member can't read peers' mail, reach another team, or another tenant).

pkg/teammailbox · invoker kind=teammate

P3 Coordination controllers

Generator→verifier convergence loop that always terminates (returns the best attempt on non-convergence — the #1 multi-agent failure mode). BudgetGuard enforces the team-wide ceiling field-wise; WidthLimiter caps concurrent members.

pkg/turnmodel/team · ConvergenceSpec

P4 Shared workspace + 3-way merge

One shared AgentFS volume across members. ThreeWayMerge reconciles two member branches against their base per file: clean merges apply, a divergent edit is a recorded conflict — turning the "two teammates, one file" risk into an enforced merge.

SharedWorkspaceSpec · team.ThreeWayMerge

P5 Bus + plan-approval + hooks

Topic pub/sub (kind=teambus) for emergent workflows. Plan-approval reuses M5: CoordinatorDecision lets the coordinator (not just a human) approve a member's gated run. Team hooks → allow / veto / requeue.

teammailbox Bus · team.CoordinatorDecision · team.EvaluateHooks

How to use it

1 · Declare an AgentTeam

A team names a loop-mode lead (coordinator) and its members (each a same-namespace Agent), picks a coordination pattern, and carries a team-wide budget ceiling.

apiVersion: runtime.agents.smol-agents.ai/v1
kind: AgentTeam
metadata:
  name: research-squad
  namespace: tenant-a
spec:
  lead: coordinator            # loop-mode coordinator Agent (same namespace)
  pattern: generator-verifier  # orchestrator | generator-verifier | team | bus | shared-state
  members:
    - { name: generator, agentRef: writer-agent }
    - { name: verifier,  agentRef: critic-agent, role: critic }
  maxMembers: 4                  # width cap (the A2A MaxDepth analog)
  budget:                       # TEAM-WIDE hard ceiling; member usage rolls up field-wise
    maxSteps: 200
    maxTokens: 1000000
    maxWallClockSeconds: 1800
    maxToolCalls: 100
  convergence:                  # MANDATORY for generator-verifier / bus / shared-state
    maxIterations: 5
    criteria: "every claim cites a primary source"
    timeBudgetSeconds: 600
  sharedWorkspace:              # optional blackboard
    sizeGiB: 5
    conflictMode: branch-merge   # shared-rw (default) | branch-merge (3-way merge)

2 · Give members team tools

Members get coordination capability by referencing Tools of the new kinds. Each tool's invoker is wired only inside a team context — fail-closed everywhere else, exactly like A2A.

apiVersion: runtime.agents.smol-agents.ai/v1
kind: Tool
metadata: { name: tasks, namespace: tenant-a }
spec:
  kind: task          # also: teammate (mailbox), teambus (pub/sub)
  description: "Claim and complete work on the team's shared list"
  inputSchema: { type: object }
  outputSchema: { type: object }

3 · The operator wires the team context (deployment-gated)

When the live coordinator spawns a member, the operator injects the team context as env, which the in-pod Wire*Invoker functions read to bind the NATS KV / mailbox / bus with the member's scoped credential:

TEAM_NATS_URL=nats://nats.tenant-a.svc:4222
TEAM_NAMESPACE=tenant-a
TEAM_NAME=research-squad
TEAM_MEMBER=generator          # this member's name → claim owner, mailbox inbox, From
TEAM_NATS_CREDS=/var/run/team/nats.creds   # per-member, scoped by the operator

Team tools in the loop

An agent calls these like any tool — the model emits a tool call with a JSON arg; the invoker dispatches on op and returns structured output.

    complete | create

// claim a unit of work

  "id":"task-3" }

    "task":{…} }

  "topic":"findings",
  "body":"found X" }

The generator-verifier loop (P3)

① generate
coordinator delegates to the generator member (A2A)
→
② verify
delegate the output to the verifier with explicit criteria
→
③ accept?
accepted → done; else feed back & repeat
↺
④ stop
maxIterations / time / team-budget → return best attempt

Governance — enforced, not advisory

This is what a local agent-team tool cannot do. Everything below is enforced by the operator / broker / NATS:

  • Team budget — a hard ceiling; member usage rolls up field-wise (steps/tokens/toolCalls/wallclock, never Usage.Add). A team cannot out-spend it. Cost stays milli-USD, observability-only.
  • Per-member isolation — every member is still a normal run/session: kata microVM in prod, default-deny egress floor, secretless broker, hardened PSA. A team adds no weaker posture.
  • Mailbox/task ACLs — a per-member NATS JWT: publish in-team, subscribe only your own inbox. Cross-member / cross-team / cross-tenant access is structurally impossible.
  • Subtree GC — the team OwnerReference owns members (literal team UID, not the downward-API pod uid — the A2A child-GC bug); deleting the team reclaims the whole tree.
  • Fan-out ceilings — maxMembers width + per-member maxConcurrent generalize the A2A recursion guard.
  • Mixed-trust teams — members are independently sandboxed + ACL'd, so a team may include a lower-trust member (e.g. an untrusted "devil's advocate") whose egress/tools are tighter than the lead's.

⚙ Deployment-gated (honest status)

P0–P5 are code-complete + unit-tested (both modules green under -race; the CRD is server-dry-run-validated) — the same bar as the M1–M5 milestone set.
