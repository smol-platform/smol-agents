The 5 picks

#1
Observability · stream modes

Live per-Step turn event stream over NATS (updates/debug/tasks modes)

85my confidence
skeptic 77
effort M
LangGraph
LangGraph stream modes `updates` (state delta per node), `tasks` (node start/finish + result/error), and `debug` (checkpoints+tasks). LangGraph emits these incrementally as the graph runs; today smol-agents only has the FINAL state.
Maps to
pkg/agentruntime.Executor.Run (the plan-act-observe loop) + pkg/sessionqueue (NATS JetStream) + the executor's already-defined-but-UNCALLED otel.go StartStepSpan/StartRunSpan + cmd/agentgateway (gateway tails the stream for synchronous callers).
Build
1) Add an optional `StepSink interface{ Emit(ctx, v1.Step) }` field on agentruntime.Executor; call it at each of the ~9 `steps = append(...)` sites in executor.go (Plan, ToolCall, Observation, *Rejected, Final) right after the append — same v1.Step value, zero new data model. nil sink = today's behavior exactly. 2) Wrap each step in StartStepSpan (currently dead code) so the OTel trace gains per-step child spans under StartRunSpan, finishing R-AM-OBS-1. 3) New NATS impl `sessionqueue` subject `agentsession.<key>.progress.<turnID>` (one append-only message per Step, ephemeral/short MaxAge so it does NOT compete with the durable .turns/.result retention). Worker (turnmodel.RuntimeExecutor) injects a StepSink that publishes there. 4) cmd/agentgateway gains `GET .../turns/{id}/events` (SSE) that SubscribeSync's the progress subject and relays until the .result lands. Per-namespace NATS ACL: the progress subject sits under the existing `agentsession.<ns>.*` ACL tree, so no new tenancy surface (D1).
Reuses
Reuses v1.Step (no new schema), sessionqueue.NATSQueue + its per-ns ACL model, the QueueSource/QueueSink seam in cmd/agent/serve_session.go, and the already-present (dead) StartStepSpan/StartRunSpan helpers in agentruntime/otel.go.
Risks
Steps carry tool args/results — must run them through the existing pkg/agentmodel/v1/redact.go before publishing or progress leaks what status redaction hides (D1/secretless). Progress stream is at-most-once/lossy by design (ephemeral) so it must never be the source of truth — the durable .result stays authoritative; document that the SSE relay can miss steps on reconnect. Emitting per-step adds a NATS publish per loop iteration; at D10 ~100s concurrent that is publish amplification — needs the ephemeral/drop-on-slow-consumer stream config, not file storage. Strictly observability: must NOT gate on it (cost stays milli-USD obs-only; never read usage.toolCalls).
Why ≥80
Net-new and absent from everything shipped: A2A, AgentTeam P0-P5, M5, and AgentSession all deliver only FINAL turn state (confirmed: Steps land in status solely at the end via RedactSteps). This adds the missing real-time per-Step observability rail — live updates/tasks/debug streaming for interactive synchronous callers and for debugging long loops — faithfully mapping the LangGraph stream-modes concept. It also closes a genuine dead-code loose end (StartStepSpan/StartRunSpan unwired → finishes R-AM-OBS-1 per-step OTel child spans) and reuses v1.Step with zero schema change. Value is observability, not new agent/orchestration capability, so it is useful and infrastructure-completing rather than transformative.

#2
Composition · Send map-reduce

Send-style dynamic fan-out tool (kind=fanout): one tool call spawns N parallel child runs over a runtime list, with a typed fan-in reducer

84my confidence
skeptic 79
effort M
LangGraph
Send API map-reduce: a node emits Send(node, state) for each item in a list computed AT RUNTIME, producing N parallel branches that fan back into a reducer-typed channel. Unlike static parallel edges, the fan-out width and payloads are decided by the running step.
Maps to
New ToolKind `fanout` + FanoutInvoker in pkg/agentruntime/invokers. The shipped A2A AgentRunInvoker spawns exactly ONE child per LLM tool call and blocks on it; the shipped team task list (kind=task) is PULL-based over a pre-seeded list. Neither is push-based runtime map-reduce. FanoutInvoker takes args {agentRef, items:[...], maxParallel} and spawns one child AgentRun per item (each item becomes that child's spec.input), bounds in-flight children by min(maxParallel, a new FanoutWidthLimit), waits for ALL to reach terminal, then REDUCES their folded outputs into a single Observation via a declared reduce mode (concat-array | merge-object | first-success). It is the A2A blocking-and-fold pattern generalized from 1 child to N with an explicit reducer and a width cap.
Build
1) pkg/agentmodel/v1/types.go: add ToolFanout ToolKind="fanout" (+Valid/SupportedLoopToolKinds); add FanoutTargetSpec{Ref ToolRef; MaxParallel int32; Reduce string(enum concat|merge|first-success); PerItemMaxTokens int64} on ToolSpec. 2) pkg/agentruntime/invokers/invoker_fanout.go: reuse AgentRunInvoker's child-spawn + terminal-poll + field-wise usage-fold logic (factor the single-child spawn/poll into a shared helper both invokers call), run them under a bounded-concurrency semaphore exactly like SessionWorker.processTurns at width>1, then fold child usages FIELD-WISE (never Usage.Add) into the returned Observation and apply the reducer to outputs. 3) Recursion + width guards: each fanned child inherits Depth+1 and is refused past A2A_MAX_DEPTH (same env/guard as A2A), and total in-flight is capped by min(MaxParallel, operator flag SMOL_AGENTS_FANOUT_MAX_WIDTH via new env FANOUT_MAX_WIDTH injected in operator/internal/builders/agentrun.go) — fail-closed if env absent. 4) registry.go: WireFanoutInvoker behind the same in-cluster-client/POD_NAMESPACE gate as WireAgentInvoker. 5) ownerRef every child to the parent run (the existing ParentRunUID subtree-GC path) so a cancelled/deleted parent GCs the whole fan-out.
Reuses
Directly reuses the AgentRunInvoker child-spawn/poll/terminal/usage-fold machinery (factored into a shared helper), the A2A Depth/MaxDepth recursion guard + ownerRef subtree GC, the field-wise usage roll-up invariant, and the bounded-concurrency semaphore pattern already in SessionWorker.processTurns. Distinct from kind=task (pull-based, pre-seeded) and kind=agent (single child).
Risks
(a) Width/blast-radius vs D10: N runtime-controlled children could blow per-namespace concurrency caps; MaxParallel must be HARD-clamped by the operator FANOUT_MAX_WIDTH and every child must still pass the per-namespace admission queue (no cap bypass) — this is the central safety property. (b) Combined with A2A depth, fan-out can multiply the subtree (each child could itself fan out): the existing A2A_MAX_DEPTH must bound depth AND a separate width product guard is prudent; be honest that depth*width can be large. (c) Partial failure semantics: define up front whether one failed child fails the whole fanout or the reducer tolerates misses (first-success tolerates; concat/merge should surface partial + error count, never silently drop). (d) Reducers are JSON-shape ops only — no AgentFS file-tree merge (still OPAQUE-BLOB), so 'merge the children's workspaces' is out of scope for v1. (e) milli-USD stays obs-only; MaxParallel/width gating is on COUNT, never on cost or toolCalls.
Why ≥80
Genuine net-new orchestration: push-based runtime map-reduce where fan-out width and per-child payloads are decided by the RUNNING step (LangGraph Send). Verified distinct from all three shipped patterns: A2A spawns exactly ONE child per tool call (invoker_agent.go), kind=task is PULL-based over a pre-seeded list with self-claim (invoker_task.go), and AgentTeam is a durable cooperative team (mailboxes/bus/convergence loop), not a single-call dynamic N-way fan-out with a declared typed reducer (concat/merge/first-success). Fills the real gap between A2A (1) and a full team, with the safety story already backstopped by the namespace admission queue.
beads: knative-agents-iru.1
#3
LLM-as-judge · verifier primitive

Calibrated LLM-judge verifier primitive (pkg/agentjudge) behind the VerifierFunc + agentbench oracle seams

82my confidence
skeptic 76
effort M
LangGraph
LLM-as-judge returning a STRUCTURED verdict (score + pass/fail + comment) against first-class criteria, plus calibration / bias-awareness (a judge is itself a fallible LLM call). LangSmith's reference-free vs reference-based rubric distinction.
Maps to
NEW package pkg/agentjudge exposing Judge.Grade(ctx, JudgeSpec, candidate, refs) (Judgment{Pass bool; Score int; Feedback string; Usage v1.Usage; JudgeModel string}). It is built on the existing LLM interface (pkg/agentruntime LLM.Chat with response-schema-constrained output), so a judgment is one bounded LLM call whose tokens fold FIELD-WISE into v1.Usage. Two concrete adapters: (a) a team.VerifierFunc adapter so the generator-verifier loop in pkg/turnmodel/team/convergence.go swaps its ad-hoc A2A verifier for a calibrated judge driven by ConvergenceSpec.Criteria; (b) an agentbench OracleImpl (kind="llm_judge") registered in operator/internal/agentbench/oracles.go returning the package's native Verdict{Kind,Evidence} from the judge's pass/score/comment.
Build
1) pkg/agentjudge: JudgeSpec{Criteria string; Rubric []Criterion{Name,Weight,Guidance}; Reference *string (nil => reference-free); Model v1.ModelRef; MaxTokens int} + Judge.Grade using LLM.Chat with a constrained verdict schema {score 0-100, pass bool, perCriterion[], comment}. 2) Calibration: a CalibrationSet (golden (candidate,expectedPass) pairs) + Judge.Calibrate() that reports judge agreement-rate, so a judge is gated by measured accuracy before use (honest about fallibility). 3) Bias controls baked in: shuffle/strip ordering for any pairwise mode, and a verbosity-neutralizing instruction in the system prompt. 4) Adapter funcs JudgeAsVerifier(JudgeSpec) team.VerifierFunc and the llm_judge oracle. Add ConvergenceSpec.JudgeModel *v1.ModelRef (hand-edit CRD per the drift rule + hand-written deepcopy) so the loop's judge model is declarable and separable from the generator model.
Reuses
Reuses the generator-verifier loop's existing VerifierFunc seam (convergence.go) and its field-wise addUsage; reuses agentbench's OracleImpl registry + Verdict type; reuses pkg/agentruntime LLM interface + v1.Usage + v1.ModelRef. Net-new: there is currently NO LLM-based verifier or judge anywhere (the team verifier is an undefined A2A call; every agentbench oracle is deterministic string/jsonpath/grep — output_match is exactly the brittle exact-match this replaces).
Risks
The judge is itself a fallible, token-costing LLM call: a mis-calibrated judge silently passes bad answers or loops the convergence loop to max-iterations — mitigated by the CalibrationSet agreement-gate and by keeping milli-USD cost OBSERVABILITY-ONLY (the judge's tokens are folded field-wise, never a gate; never touch usage.toolCalls). D1 isolation: the judge LLM must be the run's own per-namespace ModelProvider (no shared cross-tenant judge endpoint), else a judge call leaks one tenant's candidate text to another's provider. Position/verbosity bias is real and only partially mitigated by prompt + shuffle. Determinism: agentbench's runner advertises deterministic oracles; an llm_judge oracle is inherently non-deterministic, so it must be opt-in per case and excluded from the strict-equality tiers.
Why ≥80
Genuine net-new, not a restatement of shipped work: there is currently NO LLM-based verifier/judge anywhere. The team verifier has no live impl (only team_test.go references RunGeneratorVerifier), and every agentbench oracle is deterministic string/jsonpath matching, so output_match cannot grade semantic correctness. A calibrated judge gives agentbench (live runner, immediate consumer) a reference-free/reference-based semantic oracle, and gives the generator-verifier loop its first real VerifierFunc. Decision compliance is strong and explicit: tokens fold field-wise as observability-only and never gate, usage.toolCalls untouched, D1 per-namespace provider required, and fail-closed via a CalibrationSet agreement-gate + opt-in/strict-tier-excluded non-determinism. The risk section is the rare judge proposal that confronts its own fallibility/cost, which is exactly the bar. Held under 80 only because the stated M effort understates two un-budgeted seam extensions and the convergence consumer's value is deferred until a live coordinator exists (the agentbench consumer is live).

#4
Memory · episodic recall

Episodic memory: record run episodes + pre-run few-shot recall (wire the dead eventlog/episodes path)

81my confidence
skeptic 63
effort M
LangGraph
LangGraph episodic memory = 'past experiences/actions, typically implemented via few-shot example prompting, where agents learn from past sequences.' Recall of relevant prior episodes is injected to steer a new run.
Maps to
The backend already exists and works: pkg/memory/backend_eventlog.go (EventLogBackend.Write appends per-tenant+namespace, Retrieve ranks). The MCP resource memory://episodes/{agentId} is advertised (tools.go:128) and routed (gateway.go:193, readEpisodesImpl) but has ZERO producers and readEpisodesImpl is a stub that only ListNamespaces. Consumer seam = pkg/agentruntime executor / Turn assembly (where Instructions/Spec become the prompt). AgentRun terminal fold in agentrun_controller.go is the natural episode-write trigger.
Build
(a) Episode recorder: on AgentRun reaching a terminal Phase, the run controller (or the agent process at exit) writes one episode Document {input summary, outcome Phase, key tool sequence, TerminationReason} to an eventlog-kind MemoryStore in namespace 'episodes/<agentName>', via RetrievalService.Write. (b) Pre-run episodic recall: add `spec.memory.episodic {recall: bool, retrieverRef, topK}` to AgentSpec/AgentRunSpec; when set, agentruntime calls Retrieve(query=this run's input) against the episodes namespace BEFORE the first model call and prepends the top-K episodes as few-shot exemplars into the system/user prompt (a new TurnMemory field Episodes []Episode, populated in pkg/turnmodel like buildMemory). (c) Finish readEpisodesImpl to call Backend.Retrieve instead of ListNamespaces so the advertised resource actually returns records.
Reuses
Reuses EventLogBackend (already implemented + tested), the memory MCP gateway auth/policy/tenant/audit path, MemoryGrant read/write scoping, and the existing MemoryRetrieverRef resolution. Reuses the TurnMemory plumbing pattern (SelectMemoryStrategy/buildMemory) to carry recalled episodes into a Turn. Net-new = the two producers/consumers + finishing the stub reader.
Risks
D1 isolation: episode namespace MUST be tenant-scoped via Filter.Tenant (gateway already injects it) so one tenant's episodes never seed another's prompt — re-check at the backend. Prompt-injection: a past episode's text becomes new-run context, so a poisoned/adversarial prior run can steer a later one; treat recalled episodes as untrusted content (label/delimit them) and keep recall opt-in. Never gate on usage.toolCalls even though episodes contain tool sequences — they are observability, not a budget. Honest scope: the eventlog backend is in-memory in the e2e probe; durable episodic memory needs a persistent eventlog backend (redis-backed) which is declared but the worker default is in-mem.
Why ≥80
Activates an already-shipped-but-dead capability (the advertised episodes MCP resource that currently returns only namespace names) and turns terminal AgentRun outcomes into reusable few-shot exemplars — a learning loop that none of the shipped primitives (A2A delegation, AgentTeam coordination, M5 approval, AgentSession persistence) provide. Reuses the hardened memory MCP auth/tenant/policy/audit path and EventLogBackend isolation for free.

#5
Middleware · in-loop verifier

In-loop verifier middleware (online LLM-as-judge) reusing the generator-verifier seam, gated by M5

80my confidence
skeptic 58
effort L
LangGraph
Online LLM-as-judge / guardrail-in-the-loop: an after_model (or after_agent) hook that grades the candidate FINAL answer against a rubric and can veto+repair it (the verifier in generator-verifier, self-correction/reflection) before the loop terminates.
Maps to
pkg/turnmodel/team/convergence.go already has the exact judge abstraction (VerifierFunc, Verdict{Accepted,Score,Feedback}, RunGeneratorVerifier) but it lives ONLY in the team package and only the multi-agent coordinator drives it. The single-agent executor.go has no verification: at executor.go:201 decision.IsTerminal() immediately accepts the FinalAnswer and breaks. A middleware can intercept that terminal decision: on after_model, when the decision is terminal, run a VerifierFunc against AgentSpec.Verification.Criteria; if rejected and rounds remain, inject the Verdict.Feedback as a synthetic observation Step and continue the loop (self-repair); if rejected at the cap, fail-closed.
Build
Add a VerifierMiddleware (mw-1 package) that wraps the terminal branch via after_model. Lift team.VerifierFunc/Verdict into a shared pkg/turnmodel location (or reference it) so the single-agent loop reuses the SAME judge type as the team convergence loop — one judge abstraction, two callers. The verifier is itself an LLM.Chat call against a second ModelRef (a cheaper judge model) so it is wired through the same provider/broker path. Add AgentSpec.Verification {Criteria string, MaxRepairRounds int32, JudgeModel ModelRef, OnReject enum{fail,return-best}}. Bound repair rounds by a dedicated counter AND the existing Budget (the verifier's tokens fold field-wise into Usage; the executor's AllowsStep still backstops). For high-stakes agents, OnReject=hold routes a rejected-at-cap answer into M5: set Status.PendingAction{Kind:'verification'} (extending PendingAction beyond today's only 'pre-run' kind) so a human adjudicates via the existing spec.decision token mechanism — reusing M5 wholesale, exactly as team/approval.go's CoordinatorDecision does for a non-human approver.
Reuses
Reuses team/convergence.go VerifierFunc/Verdict/field-wise Usage roll-up (generalized from team-only to single-agent), the M5 PendingAction/Decision/token gate (team/approval.go shows the reuse pattern), and the mw-1 chain seam. The judge is the same shape agentbench's oracle.go Verdict uses, keeping offline and online verification conceptually aligned.
Risks
The judge is itself a fallible, token-costing LLM call (the brief's core caution): it can wrongly veto a correct answer (false reject -> wasted repair rounds / spurious human escalation) or wrongly accept (false pass). Mitigations: HARD-bound repair rounds via a counter never just the prompt (convergence.go's #1 failure mode is the open-ended loop, already solved there — reuse that bound); always able to return-best like RunGeneratorVerifier does on non-convergence; judge tokens are observability cost (milli-USD, never a gate) but DO count toward the token budget so a runaway judge is stopped by AllowsStep. Calibration/criteria are first-class CRD fields, not hidden. mid-loop HITL is post-GA-deferred (D6), so OnReject=hold must be opt-in and clearly flagged as extending the deferred surface; default OnReject=fail keeps it fail-closed (D3).
Why ≥80
Closes a concrete, verified hole: single-agent runs today accept the first terminal FinalAnswer with no quality gate, while the generator-verifier seam (used only by AgentTeam) sits unused for one-shot/loop agents. An in-loop verifier that injects Verdict.Feedback as a synthetic observation and re-plans (self-repair), bounded by a hard counter AND Budget, gives single-agent reliability without the cost/weight of a full AgentTeam — value beyond shipped A2A/AgentTeam/M5. Aligning the online judge shape with agentbench's offline oracle Verdict is a real conceptual win. Value is contingent on rescoping: ship only OnReject={fail(default),return-best} (both fully feasible inside the existing executor + budget), and DROP/defer OnReject=hold (it reopens the D6-deferred mid-loop HITL surface the architecture cannot currently serve). Effort L is optimistic given the middleware seam must be built and ConvergenceSpec/Verification must be added to AgentSpec with hand-edited CRD + hand-written deepcopy; closer to L-heading-XL if the hook chain is greenfielded.
